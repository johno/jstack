# AGENTS.md

jstack is a small collection of portable Agent Skills for shipping software with coding agents.

Keep it small.

## The boundary

jstack describes engineering workflows. The repo using jstack supplies the tools and conventions.

A skill can say:

> Run the repository's verification checks.

It should not say:

> Run `make ci`.

A skill can say:

> Update the work item.

It should not require Linear, GitHub Issues, Jira, or a particular API.

The same `SKILL.md` should make sense across different harnesses, source hosts, issue trackers, package managers, and branching strategies.

If portability requires adding adapters, configuration, or conditionals for specific environments, the abstraction is probably wrong.

## Skills

Skills live in:

```text
skills/<name>/SKILL.md
```

Keep them self-contained, procedural, and relatively short.

Each skill should have a clear job. Prefer adding a useful instruction to an existing skill over introducing another layer that coordinates skills.

Do not add:

- a jstack runtime
- a router or global mode
- model selection
- harness-specific APIs
- MCP dependencies
- subagent or swarm requirements
- a skill registry
- generated manifests
- compatibility adapters
- dependencies that exist only to manage a handful of Markdown files

If something can stay Markdown, keep it Markdown.

## Writing skills

Write instructions that describe the outcome and the reasoning required to get there, without prescribing infrastructure the consuming repo should own.

Prefer concrete language over framework terminology.

Good:

> Inspect the current revision before treating earlier review results as valid.

Less good:

> Invoke the review orchestration layer against the latest changeset.

Avoid filling skills with exhaustive rules for unlikely edge cases. A short instruction that gives the agent the right principle is usually more useful than another page of procedure.

When a portability problem turns up during dogfooding, fix the wording of the skill before adding machinery around it.

## Changes

Keep changes as small as the work allows. Do not mix unrelated cleanup into a feature or skill change.

Run:

```sh
scripts/check-skills.sh
```

before considering skill changes complete.

The check validates portable metadata and catches obvious assumptions about harnesses, models, trackers, hosts, package managers, merge strategies, and project-specific commands.

Treat a portability failure as a design problem, not as a reason to add another exception to the checker.

## Git and pull requests

Write commit subjects and PR titles for humans. Use plain sentences and describe the change itself.

Do not use conventional-commit prefixes like `feat:`, `fix:`, or `chore:` unless the repository explicitly adopts them later.

Keep ticket IDs out of commit subjects and PR titles when the ticket can be linked in the PR body instead.

Do not rewrite shared history casually. Preserve reviewable commits once other people or agents have started reviewing them.

### No coding-agent attribution

Never add coding-agent attribution to commits, PR descriptions, documentation, or generated files.

That includes:

- `Co-Authored-By` trailers for Claude, Codex, or another coding agent
- `Generated with Claude Code`
- `Generated by ...`
- badges or footers advertising which model wrote the code
- equivalent attribution added by tooling

Coding agents can add attribution once they're responsible for the code that ships. :)

## Code

This repo should have very little code.

When code is necessary, keep it boring and easy to audit. Prefer the standard tools already available in the environment over adding dependencies.

Comments should be sparse. Explain surprising constraints or behavior, not code that already explains itself.

Do not introduce an abstraction until there is something real to abstract.

## README

Keep the README useful and short.

It should explain what jstack is, what skills exist, how to install them, and the basic philosophy. Detailed development rules belong here rather than growing the README into a specification.

## Before shipping

For any change, check:

- Does this make jstack more useful without making it substantially bigger?
- Does the same skill still work across different coding-agent environments?
- Did repo-specific policy leak into a portable skill?
- Did we add machinery where better Markdown would have worked?
- Did the skill checker pass?

If the answer to the fourth question is yes, simplify it.
